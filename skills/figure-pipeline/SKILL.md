# 科研绘图协同总控

本技能是**调度器**，不是画图器。只做四件事：

1. 把用户请求拆成“能力需求”；
2. 在已装专门技能里做匹配与排序；
3. 编排多技能的角色、顺序与交接；
4. 校验交接结果并把下一棒交出去。

画图、统计检验、字体/栏宽、脚本参数、QA 修复，全部由子技能的 `SKILL.md` 负责。本文件不复述、不代做、不发明流程。

## 零、边界（先划清）

**总控不做：**

- 不画任何图、不写绘图代码、不生成绘图模板；
- 不跑统计检验、不编造 p 值、不决定误差棒类型；
- 不规定 DPI、栏宽、字体、色板、面板标签；这些是子技能的领域；
- 不替子技能跑 QA，也不替它修图；只确认“它的 QA 已跑并回报”；
- 不把子技能流程抄进本文件。

**总控只做：**

- 判断该找谁、谁主谁辅、先谁后谁；
- 把用户约束、输入、上游产物完整交过去；
- 收产物与 QA 状态，决定下一棒或重路由；
- 在能力缺口时如实报告，不硬凑。

## 一、能力地图（只记“谁最强”，不记流程）

详细字段见同目录 `registry.json`。核心判断如下：

| 技能 | 默认角色 | 最强能力 | 典型输入 | 典型输出 |
|---|---|---|---|---|
| **S0 `scipilot-figure-skill`** | 决策 | 数据画像、图型选择、误导性画法拦截、统计标注方案设计（不跑检验） | 数据 + 研究问题 | 选图/风险决策、首版草图 |
| **S1 `scientific-figure-making`** | 生产 | 可复现的 matplotlib 投稿图、house style、多面板基础拼版 | 数据 + 明确图型 | `plot.py` + PDF/SVG + 预览 |
| **S2 `nature-figure`** | 审计/规范（可兼任生产） | 期刊审计/修订/导出、多面板证据结构、graphical abstract、可编辑 SVG 示意图、Python/R 双后端 | 成图，或数据+图契约 | 审计报告、修订图、QA 结果 |
| **S2b `nature-image2ppt`** | 转换 | 位图/扫描 PDF → 对象级可编辑 PPTX、逐页视觉复核 | 图片/扫描 PDF | `deck.pptx` + 逐页 QA |
| **S3 `drawio-skill`** | 结构 | `.drawio` 源文件、架构/流程/泳道/UML/多视图、截图→drawio | 概念/IR/源码/截图 | `.drawio` + 导出 |
| **S4 `visio-image-rebuilder`** | 重建 | 原生 `.vsdx` 重建、改现有 Visio、多格式导出 | 参考图/现有 `.vsdx` | `.vsdx` + 导出 |

读取顺序：先 `registry.json` 看边界与依赖，再 Read 目标技能的 `SKILL.md` 全文。**每次重读，不凭记忆。**

## 二、匹配算法

### 2.1 先过四道硬约束（不满足就淘汰）

1. **输出格式**：`.vsdx` 只有 S4；`.drawio` 只有 S3；图片→PPTX 只有 S2b；期刊 PDF/SVG 从数据走 S1 或 S2。
2. **输入类型**：原始数据只能走数据图技能；已有成图优先审计；截图位图只能走转换/重建；概念正文走结构图。
3. **环境可用性**：Visio COM 不可用则 S4 淘汰；Graphviz 缺失只影响 S3 自动布局，不等于 S3 淘汰；OCR token 缺失只影响 S2b 联网识别。
4. **保密/版权**：未公开数据、患者数据、审稿材料不得交给会外传的路线。

硬约束优先于星标、偏好、点名。点名与硬约束冲突时先说明，不静默改格式。

### 2.2 给候选技能打分（0–3）

| 分 | 含义 |
|---|---|
| **3** | 主能力完全命中：任务动词、输入类型、输出格式三者都对 |
| **2** | 可承接，但需要分工/转换/二次审计 |
| **1** | 兜底：能出结果，但不是最佳 |
| **0** | 不匹配或硬约束冲突 |

排序 tie-break，依次比较：

1. 硬约束满足度；
2. 输入保真度（原生可编辑 > 重建 > 位图重绘）；
3. `best_at` 命中数（专精度）；
4. 依赖可用性（`doctor.py`）；
5. 调用成本（步骤数/外部调用），只在前四项打平时才看。

`stars` 只作为仓库成熟度参考，**不参与硬约束，也不替代专精度**。

### 2.3 判定“单技能”还是“组合”

- 只有一个 3 分主技能，且不需要二次审计 → **单技能直调**。
- 需要“先决策再执行” → **决策→生产**（S0→S1/S2）。
- 需要“先生成再规范” → **生产→审计**（S1/S3/S4→S2）。
- 需要换格式 → **转换链**（S2b/S3/S4）。
- 多张独立图 → **每图一个主技能**，S2 只做统一审计，不接管生产。
- 同一张图不允许两个主技能并行；只允许“生产者 + 审计者”两个角色。

### 2.4 匹配表（意图 → 主技能 → 辅助）

| 意图 | 主技能 | 辅助/下一棒 |
|---|---|---|
| 有数据但不知道画什么 | S0 | 决策后交 S1 或 S2 |
| 数据 + 明确图型 + 要可改代码 | S1 | S2 做投稿审计 |
| 已有成图要按期刊修/审/导出 | S2 | 无需生产技能 |
| 多面板 Figure 要证据结构与对齐 | S2（生产或审计） | 数据面板可由 S1 先出 |
| 图形摘要 / AI 示意图 | S2 | 生产草稿后仍由 S2 政策/披露检查 |
| 手绘可编辑 SVG 方法示意 | S2（vector） | 要 drawio 源则改 S3 |
| 方法框架/技术路线/架构/泳道/流程 | S3 | 要期刊风格则 S3→S2 审计 |
| 截图/白板要变可编辑 drawio | S3（raster2drawio） | 要 `.vsdx` 则改 S4 |
| 必须 `.vsdx` 或改现有 Visio | S4 | 导出 PPTX 仍是渲染页，需说明 |
| 图片/扫描 PDF 要变可编辑 PPTX | S2b | 要原生 PPT 形状则 S2b 是正确路线 |
| 多图风格统一 | S2 统一审计 | S1/S3 各自生产，不互相改图 |

## 三、协同模式

| 模式 | 角色分配 | 适用 |
|---|---|---|
| **直调** | 单一主技能 | 单阶段、边界清晰 |
| **决策→生产** | S0 出决策；S1/S2 执行 | 图型未定、风险未评估 |
| **生产→审计** | S1/S3/S4 生产；S2 审计/修订/导出 | 要投稿规范、要多面板对齐、要终审 |
| **转换** | S2b/S3/S4 单一主技能 | 只换交付格式 |
| **多图并行** | 每图一个主技能；S2 统一审计 | 一套 Figure 1–N |
| **返修复审** | 生产者改；审计者复；总控只传话 | QA 未过 |

协同铁律：

- 同一产物同一时间只有一个**生产者**；可以有多个**审计者**，但审计者不改图，只出问题清单。
- 审计者发现问题 → 退回生产者修；总控不直接改。
- 多图并行时，各图生产者互不改对方的图；统一风格由 S2 审计并给出修改项。
- 返修最多 3 轮；仍不过就报告“缺口-证据-已尝试”，不无限循环。

## 四、交接协议

### 4.1 交给子技能之前

1. Read 目标子技能的 `SKILL.md` **全文**；需要 references 时按它的指引再读。
2. 组装 **context pack**，一次交清：

| 必传项 | 内容 |
|---|---|
| 用户原话/目标 | 不加工、不改写诉求 |
| 硬约束 | 输出格式、期刊/场合、尺寸/语言、保密/版权 |
| 输入 | 原始数据/成图/截图/正文的**绝对路径** |
| 已确认决策 | 图型、统计检验、n、校正、误差类型（用户给的，不是总控编的） |
| 共享上下文 | `figure-system.json` 路径（如有，由 S2 维护） |
| 期望产物 | 具体文件与格式 |
| 验收 | 明确要求“跑你自己 SKILL.md 里的 QA 并回报结果” |

3. 不传总控自造的步骤、阈值、DPI、栏宽、模板名；这些由子技能决定。

### 4.2 子技能交付之后

收三样东西：

1. **产物路径**（存在、非空）；
2. **子技能自己的 QA 状态**（它跑没跑、结果如何）；
3. **未决问题/假设**。

然后：

- 记入协同台账（见第五节）；
- 需要下一棒 → 把产物路径与决策写进下一技能的 context pack；
- QA 未过 → 带证据退回同一生产者；再不过 → 按第六节重路由；
- **总控不替它跑 QA，也不替它修图。**

## 五、协同台账（最小记录）

复制 `assets/manifest.template.json`，只记协同事实，不记领域参数：

```json
{
  "request": "用户原话摘要",
  "slug": "fig1",
  "context": {"journal": "Nature", "format": "pdf", "figure_system": "figure-system.json"},
  "assignments": [
    {
      "figure": "fig1",
      "skill": "nature-figure",
      "role": "auditor",
      "status": "done",
      "inputs": ["..."],
      "outputs": ["..."],
      "qa": {"owner": "nature-figure", "status": "pass", "notes": ""},
      "next": ""
    }
  ],
  "handoffs": [{"from": "scientific-figure-making", "to": "nature-figure", "artifact": "fig.pdf"}],
  "open_questions": [],
  "next": ""
}
```

台账只回答：谁、什么角色、吃了什么、吐了什么、它的 QA 过没过、下一棒给谁。

## 六、失败与重路由

| 失败 | 处理 |
|---|---|
| 主技能入口缺失/依赖不可用 | 匹配阶段就淘汰，换备选；不硬跑 |
| 主技能跑不通（脚本/环境） | 先带证据退回同一技能一次；仍失败 → 换备选技能 |
| S1 不可用 | 改 S2 的 Python 路线；记录“非 S1 产出” |
| S2 不可用 | 拆分：S1 生产 + 人工/其他审计；不能声称已过期刊审计 |
| S3 不可用 | 改 S2 vector schematic（SVG），明确“不是 drawio” |
| S4 不可用 | 改 S3 `.drawio`，明确“不是 `.vsdx`” |
| S2b OCR token 未配 | 本地 builtin-ink 模式；明确“不识别文字”，不假装识别 |
| 所有技能都不匹配 | 停止，报告能力缺口与建议补齐的技能；不自己造流程 |

## 七、冲突裁决

- **格式冲突**：`.vsdx` / `.drawio` / `.pptx` 是硬约束，直接决定主技能。
- **能力重叠**：S1 与 S2 都能产数据图 → 要可改代码选 S1；要期刊终审/双后端选 S2；两者都要 → S1 生产、S2 审计。
- **S2 与 S3 都能画框架图** → 要 `.drawio` 源或架构/UML/云选 S3；要期刊风格 SVG 选 S2；两者都要 → S3 出结构，S2 审。
- **S2b 与 S4 都能出可编辑** → 要 PPTX 选 S2b；要 `.vsdx` 选 S4；两者都要且有 Visio → S4 重建一次再导 PPTX，避免两套不一致。
- **点名冲突**：点名优先，但格式硬约束更高；冲突时说明并让用户二选一。

## 八、自检与更新（只保协同可用）

- **自检**：`python scripts/doctor.py` 检查 registry schema、入口、关键文件、Junction、依赖与环境；`--deep` 加 Graphviz/drawio/image2ppt/后端探测。
- **更新**：`python scripts/update.py` 拉取所有子技能仓库、打印变更文件并自检；`SKILL.md` 变更时提示复核能力地图。
- **不缓存流程**：每次调用前 Read 子技能 `SKILL.md` 全文。
- **只改能力地图**：子技能改流程不改总控；只有能力边界/入口/依赖变化才改 `registry.json`。
- **禁止复制**：子技能只存在一份，豆包只放指向 zcode 入口的 Junction。

## 九、示例

- “这组数据不知道画什么，投 Nature 子刊” → 主 S0；决策后交 S1 或 S2。
- “从原始数据到投稿 Figure 1” → S0→S1→S2；总控只编排，不改图。
- “已有 PDF 图，按期刊修字号和碰撞” → 主 S2，单技能直调。
- “三张图风格统一” → 每图一个主技能；S2 统一审计，输出修改项，不接管生产。
- “给三组加显著性，n=6” → 用户给检验/校正；S0 设计标注，S1 画，S2 审。
- “画方法框架图，要能继续编辑” → 主 S3；要期刊风格则 S3→S2。
- “截图转可编辑 Visio” → 主 S4；只要 drawio → S3。
- “截图转可编辑 PPT” → 主 S2b。
- “做一张图形摘要” → 主 S2，按其 graphical abstract 路线。
- “只把这张图换个颜色” → 按源格式直调 S2/S3/S4，单阶段。
- “从零做一套答辩 PPT” → 不归本技能，走 PPT 技能。

## 十、硬规则

1. 总控不画图、不做统计、不写绘图代码、不跑 QA 修复。
2. 同一产物只有一个生产者；审计者只出问题清单。
3. 硬约束（格式/输入/环境/保密）优先于星标、偏好和点名。
4. 每次调用前 Read 子技能 `SKILL.md` 全文，不凭记忆。
5. 交接必须给绝对路径与已确认决策；禁止让下一棒猜。
6. 子技能的 QA 是唯一质量事实源；总控只确认它跑过并记录。
7. 返修最多 3 轮；仍不过就报告能力缺口，不无限循环。
8. `stars` 只是成熟度参考，不替代专精度与可用性。
9. 不把子技能流程抄进总控；总控只存能力地图与协同规则。
10. 任何降级都要在交付说明中写明“换了哪个技能、为什么、产物差异是什么”。
